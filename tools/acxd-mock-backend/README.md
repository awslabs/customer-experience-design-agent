# acxd-mock-backend — fixed, shipped mock API tool

A deterministic deployed backend for the APIs a solution generates: **one API Gateway → one path-routing
Python Lambda → bundled JSON per API**, all deployed as nested stacks of ONE parent stack in one command, with an x-api-key/usage-plan contract, access logging, and
explicit region pinning. Like `acxd-deploy-engine`, the code here is **fixed and tested** — the harness
does **not** author it per engagement. It is copied into a project's `backend/mock-integration/` at
distribution; the agent supplies only declarative content.

## What is fixed vs what the agent authors

**Fixed (shipped, never re-authored):**
- `cdk/stack.ts`, `cdk/app.ts`, `cdk/cdk.json`, `cdk/package.json` — the whole CDK app. CommonJS
  (so `__dirname` resolves), region from context/config (never ambient), api key.
- `handler.py` — the handler CORE: `/{operation}` routing (at the API Gateway stage root), param parsing, response envelope,
  generic **plain-lookup**, and auto-discovery of per-op overrides.
- `validate.py` — pre-deploy check + operation-surface report.

**Agent authors (per engagement), one folder per generated OpenAPI file, named by its API id:**
- `apis/<apiId>/data/<operation>.json` — one file per operation of that API (1 to N — the count is data).
- `apis/<apiId>/ops/<operation>.py` — OPTIONAL, only for a **computed** operation (see below).
- `mock.config.json` — OPTIONAL tuning: `stageName`/`memoryMb`/`timeoutSeconds`. Project name, region and
  environment come from the distribution-root `.env`.

## Security posture (cdk-nag exemption)

This mock stack is **intentionally exempt from cdk-nag**. That is a scoped decision, not a relaxation of
security — cdk-nag still runs at full strength, and must pass with zero findings, on the production
`backend/adapter-integration/` stack (the one that fronts a real customer system). The exemption applies to
this stack alone because:

- **It holds no real data.** Everything served is synthetic JSON authored for a demo/POC — there is no PII or
  customer data to protect.
- **It is throwaway.** The mock is deleted once the live integration is ready; it never becomes production
  and never fronts real data, so IaC hardening on it has negligible value.
- **The findings do not apply.** For example `AwsSolutions-APIG2` asks for request-*body* validation, but the
  mock API is one generic `/{operation}` route serving every operation of that API, so there is no single body model to validate
  against; the handler parses each body itself. Request *parameter* validation is enabled.

If a customer's security process requires every synthesised stack to pass cdk-nag regardless, deploy this
mock only to a sandbox (or not into their account at all) rather than re-enabling cdk-nag on throwaway
synthetic infrastructure. Real security gating belongs on the adapter stack, where it remains enforced.

## Two operation classes

- **Plain-lookup** (most operations): the core returns `data[key(params)]` or `data["_default"]`.
  Zero code — just author `apis/<apiId>/data/<operation>.json`. Keys are matched canonically (upper-cased,
  non-alphanumerics stripped), so a caller value of `CUST-1001` matches a data key of `CUST1001`.
- **Computed** (e.g. a quote calculation, a PIN check): drop `ops/<operation>.py` exposing
  `handle(params, data) -> dict`. The core auto-discovers and calls it; if absent, it falls back to
  plain lookup. (Copy `ops/getQuote.py.example`.) The CDK/routing/envelope are never touched.

The `{operation}` path segment, `apis/<apiId>/data/<operation>.json`, and `apis/<apiId>/ops/<operation>.py` all share the same
camelCase operation id — the same id the ACXD flows call.

## Usage

```bash
# 1. Author apis/<apiId>/data/*.json (+ any ops/*.py) for each API (ops/getQuote.py.example is a computed-op template).
# 2. Validate — reports each API's operations and fails loudly on any problem.
python3 validate.py

# 3. Deploy every API with one command from cdk/. Project name, region, environment and each API's key
#    (<API>_KEY, generated by openapi-wiring-cli.ts --generate-keys) come from the distribution-root .env.
#    CDK bootstrap is a one-time Prerequisites step, not part of this command.
cd cdk
npm install
npm run deploy
#    Stack: acxd-<projectName>-<env>-mock-apis (one nested stack per API).

# 4. Put each <ApiId>Url output into that API's <API>_URL in the distribution-root .env, as shown (the engine
#    trims a trailing slash; the data request appends /<operation>). The keys are already there.
```

## Request/response logging

`handler.py` logs every call to CloudWatch (via the Lambda log group) at INFO:
- **On request:** `ACXD-MOCK request: operation=<op> params=<query-string/body JSON>`
- **On response:** `ACXD-MOCK response: operation=<op> payload=<response JSON>`

This lets a tester confirm what the ACXD console actually sent (operation path + params, including
how slots formatted a value) and what the mock returned, without adding ad-hoc logging. Find it in the
mock Lambda's CloudWatch log group.

## Test identities — surface them in the deploy runbook (do NOT make testers open the Lambda)

Testers in the ACXD console need to know which customer/account values the mock will accept. Those values
live in the seeded `apis/<apiId>/data/*.json` files (e.g. account numbers + PINs in `verifyIdentity.json`, customer ids in
any lookup operation). Do **not** make a tester open the Lambda or the JSON to find them.

**Authoring instruction (agent, at backend build / deploy time):** in the Mock Integration deployment section
of the project runbook, list the seeded test identities for THIS project, read from the generated `data/*.json`
files. Produce a small table per keyed operation, for example:

```
### Mock test identities (example — regenerate from this project's data/*.json)

verifyIdentity (existing-customer auth):
| Account number | PIN  | Customer name |
|----------------|------|---------------|
| ACC10021       | 4821 | Sam Rivers    |
| ACC10022       | 1234 | Alex Morgan   |
| ACC10023       | 9999 | Jordan Lee    |

accountExists / getHeldPolicies / getQuote: list the keyed values each accepts (and any _default behaviour).
```

The values above are ILLUSTRATIVE (from one earlier project) — always regenerate the table from the actual
`data/*.json` this project ships, because the identities are synthetic and authored per engagement.

**Adding custom test identities BEFORE deploying:** append entries to the relevant `apis/<apiId>/data/<operation>.json`
(e.g. add an account to `verifyIdentity.json` with its `pin` + `customerName`), keeping the existing key
shape. Because keys are matched canonically, `ACC-10024`, `ACC10024`, and `acc 10024` all resolve to the same
record — key the data however reads best. Re-run `python3 validate.py`, then deploy. No handler or flow change
is needed; the new identity is testable as soon as the mock redeploys.

## Contract (unchanged from the ACXD data-request rules)

- Request values are read from the JSON body AND the URL query string, merged (the body wins on a clash). The
  JSON body is the preferred mock channel (POST writes, sensitive values such as a PIN); GET lookups via URL
  params also work. Nested body objects/arrays reach your op as nested dicts/lists.
- **Field names are the contract — match your data request's responseSchema EXACTLY.** The keys your op
  returns (and the params it reads) must match, character for character, the field names in that operation's
  `responseSchema` (and URL params) in `resources/data-requests.json`. ACXD maps response fields to
  `{dataRequest.field}` by exact name — a mismatch resolves BLANK downstream with no error. The names in
  `ops/getQuote.py.example` (`basic`, `customerPlus`, `finalPricing`, …) are ILLUSTRATIVE — do not copy them
  verbatim; rename every returned key to your own operation's schema.
- Responses are flat top-level fields (no envelope, no nesting the flow can't read).
- Business-logic failures return HTTP 200 with a boolean flag; non-200 = real system error.
- No data store — responses are served from the shipped JSON. Migrating to a live backend is a
  data-request URL/secret swap with no ACXD flow changes; delete the mock when the live backend exists.

## Module mode

`cdk/package.json` is **CommonJS** (no `"type": "module"`) so the Lambda-asset path
(`path.join(__dirname, "..")`) resolves natively. Do not add `"type": "module"`.
